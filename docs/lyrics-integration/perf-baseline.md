# 歌词链路性能基线

> 一句话结论：**我们自己的代码每帧只花约 1.6 µs（33 ms 预算的 0.005%），
> 分配约 499 B/帧。** 帧率不是这个功能的瓶颈；真正的开销在 SMTC 跨进程采样与
> WPF 渲染，两者都不在本基线的测量范围里（见「口径」）。

## 口径：这份数据测了什么、没测什么

| | 说明 |
|---|---|
| **测了** | `FluentFlyout.Lyrics` 与 `Frames/` 里的纯 CPU 工作：解析、文档投影、整首定宽、取帧、节流与去重 |
| **没测** | SMTC 的跨进程采样（`MediaManager` → `GetPlaybackInfo` / `GetTimelineProperties`），需要真的在放歌 |
| **没测** | WPF 的布局与渲染（`TaskbarWidgetControl` 改可视树），需要 UI 线程与真实任务栏 |
| **近似** | 文本宽度用 `chars × 7.0` 代替 `StringWidth.GetStringWidth`。宽度算法的复杂度不受影响，绝对值不用于对比像素 |

**为什么不报「合并前 vs 合并后」**：歌词是新增功能，`master` 上没有对照组。
这份数据报的是「**开启歌词之后新增的**单帧开销」，不是「改动前后对比」。

## 复现

```bash
FF_PERF=1 dotnet test FluentFlyout.Lyrics.Tests --filter LyricsPerfBaseline
```

不设 `FF_PERF=1` 时该用例只校验夹具（解析与投影可用），不采样——耗时数据随机器与负载
浮动 2–3 倍，任何写死的阈值都会变成「在别人电脑上挂」的假失败，所以这里**不做断言**。

样本：合成 LRC 200 行（中英交替，中文 12–16 字、英文 30–40 字符），
每行间隔 4 秒，整首约 13 分钟。测量环境：本机开发机，Windows，.NET 10.0.14，Release，单线程同步执行。

## 结果

| 场景 | 频率 | 平均耗时 | 每次分配 |
|---|---|---|---|
| 解析 LRC（整首 200 行） | 每首歌 1 次 | 0.14 – 0.18 ms | 207.7 KB |
| 建立文档（投影 + 去信息行） | 每首歌 1 次 | 0.33 – 0.39 ms | 81.2 KB |
| 整首定宽（取最宽一句） | 每首歌 1 次 | 5.3 – 6.2 µs | 0 B |
| 每帧取帧（`GetDisplayFrameAsync`） | 30 次/秒 | 0.6 – 0.8 µs | 440 B |
| 每帧全链路（节流 + 取帧 + 去重） | 30 次/秒 | 1.5 – 1.7 µs | 499 B |

区间是连续三次采样的最小/最大值，用来表示稳定性，不是误差范围。

## 怎么读这组数

1. **换歌的一次性开销约 0.5 ms、分配约 290 KB**，相对于一次真实网络检索（实测 0.75 s 量级）
   完全可以忽略——它藏在「等歌词返回」的时间里。
2. **每帧 1.6 µs / 499 B**。按 30fps 折算，1000 帧（约 33 秒）累计 1.65 ms；
   分配 14.6 KB/s，gen0 回收几乎不会有感知。这一段没有优化空间，也不需要优化。
3. **真正的每帧成本不在这里。** SMTC 采样是跨进程 COM 调用，量级通常比 1.6 µs 高两三个数量级，
   这也正是两处设计存在的原因：
   - `LyricFramePumpCore.DefaultInterval` 取 33 ms（30fps）而不是跟随渲染帧率 16 ms；
   - 关掉歌词就 `Stop()` 停泵（`LyricsService.SetEnabled(false)`）——空转的定时器每秒要做 30 次跨进程调用。
4. **`整首定宽` 0 分配**，因为它只遍历 `LyricLine` 列表、结果是 `double`。
   抽样上限是 `DefaultMaxMeasuredLines = 600` 行：本样本 200 行低于上限、逐行实测；
   超过 600 行才等距抽样。所以它的成本有上界，最长的那首歌也不会把换歌时间拖长。

## 结论

- 这组数字支持「歌词不会拖慢任务栏小组件」这个判断，**但不构成对真实帧率的证明**：
  真实帧率还取决于 SMTC 往返与 WPF 布局，两者都必须在真机上测。
- 若将来有人在 `GetDisplayFrameAsync` 里加了每帧的字符串拼接、LINQ 分配或正则，
  这条基线会立刻被打破（499 B/帧 → KB 级）。**这是它作为回归参照的主要用途**：
  改完重跑一次，看这两个数是否还在同一量级。
